# FlowPilot 企业级 Agent 学习与演进手册

## 1. 这份手册解决什么

企业 Agent 的难点很少停留在“模型能不能答”。真正进入生产链路后，问题通常出现在检索证据、长任务恢复、并发一致性、审批重放、远程副作用、租户隔离和指标真实性上。单次修补 Prompt 往往只能遮住症状，下一次换模型、换工具或发生重试时，同一问题会以另一种形式出现。

本手册供 S1～S7 在设计、开发、故障注入和交接时共同使用，记录三类内容：

- 行业中反复出现、可在本项目复现的工程难题。
- FlowPilot 用什么结构处理这些难题，以及结构成立所依赖的边界。
- 实现和运行中得到的新证据、失败案例与后续调整。

它不是契约、ADR 或验收状态的替代品。成熟结论必须回流到对应 ADR、`contracts/**`、工作包和 Traceability；实测结论必须带代码版本、数据版本、运行命令和证据。没有证据时，只能写“假设”或“设计”，不能写成项目成绩。

## 2. 结论如何成长

一条经验按以下路径演进：

```text
现场信号
  → 可重复的问题
  → 失败机理假设
  → 架构结构或约束
  → Work Package 实现
  → 故障注入与负向测试
  → 独立验证
  → ADR / 契约 / 验收基线
```

每次记录使用四种证据等级：

| 等级 | 含义 | 允许写法 |
|---|---|---|
| `HYPOTHESIS` | 有现象或行业经验，尚未在 FlowPilot 复现 | 待验证、可能、假设 |
| `DESIGNED` | 已有架构结构、契约或验收定义 | 设计为、计划采用 |
| `IMPLEMENTED` | 已有代码与单元/契约测试，未完成独立验收 | 已编码、实现中 |
| `VERIFIED` | 固定环境中由独立角色复现并有有效证据 | 已验证 |

这里的等级只描述某条工程经验的成熟度。产品功能的正式状态仍以 `docs/acceptance/traceability.v1.json` 为准。

### 2.1 日常学习闭环

学习积累不依赖七个会话每天向 S1 发送长篇总结。责任会话只在 Handoff 中增加结构化 `LEARNING_CANDIDATE`：

```text
LEARNING_CANDIDATE=<none|短标题>
MATURITY=<HYPOTHESIS|DESIGNED|IMPLEMENTED|VERIFIED>
TRIGGER=<什么现象触发>
MECHANISM=<可复核的失败机理摘要>
STRUCTURE=<采用或建议的结构>
EVIDENCE=<提交/测试/报告/最小复现>
RESIDUAL_RISK=<残余风险>
TARGET=<playbook section|ADR|work package|none>
```

规则：

1. 常规做法、一次性环境噪音和没有新机理的重复故障写 `none`。
2. 会影响契约、安全、恢复或多个会话协作方式的问题，在本轮 Handoff 提交候选，不等待集中复盘。
3. S1 在集成或迭代结束时批量归并，去重后写入本手册；不复制聊天记录和隐藏思考。
4. 得到独立复现后升级成熟度；推翻旧结论时保留适用条件和反例，不直接抹去历史。
5. 已成熟的产品约束进入 ADR/契约/验收；研发协作经验进入团队协议和工作包模板。

## 3. 结构先于补丁

FlowPilot 的核心结构与它们防住的失效模式如下。

| 结构 | 主要避免的问题 | 仍需验证的边界 |
|---|---|---|
| LangGraph 唯一持久状态机 | 多套编排各自保存状态、长链路断点丢失、恢复后走错分支 | Checkpoint 一致性、图版本迁移、旧 Worker fencing |
| Domain / Application Port | 领域规则被框架、Provider 或数据库实现绑死 | Port 语义是否足以覆盖并发、事务与稳定错误 |
| 分层 `ContextEnvelope` | 长对话膨胀、指令漂移、Handoff 继承过量权限 | 裁剪可解释性、分类上限、Token 与质量回归 |
| MCP Gateway + PDP/PEP | Agent 绕过授权直连工具、工具描述注入、凭据扩散 | 双主体认证、Schema 固定、出站控制、DLP |
| PlannedAction / Approval / Ledger | 批准后改参数、重复写、超时后盲重试 | 摘要、策略、Schema、过期时间的完整绑定 |
| PostgreSQL 事实源 + Inbox/Outbox | Redis 丢失即丢任务、事务提交后漏事件、重复投递 | RLS、序号缺口、回滚、重投和并发唯一约束 |
| Checkpoint / Lease / Fencing | 旧 Worker 恢复后与新 Worker 同时推进同一任务 | 租约过期、`run_generation`、进程崩溃窗口 |
| Trace / Audit / Security 分流 | 采样导致合规证据消失、日志泄密、阻断原因不可追踪 | 不可采样存储、双向关联、哈希链与外部锚 |
| 固定 Dataset + 确定性 Gate | 删除失败样本美化指标、Judge 替代安全判断 | 数据哈希、固定分母、Judge 校准与盲测 |

结构不会自动带来正确性。只有对应的失败路径能被稳定复现，并且自动化测试证明结构在并发、重启、超时和恶意输入下仍成立，结论才可以升级。

## 4. 重点难题

### 4.1 检索结果看似相关，但答案仍不可信

**关联功能：** FP-SEC-003、FP-EVAL-001、FP-EVAL-003

常见症状包括召回了过期 SOP、跨租户文档进入候选集、答案引用存在但不支持结论，以及 Rerank 把语义相近的错误版本排到前面。只调向量模型或 Top-K 无法同时解决时效、权限、版本和证据充分性。

FlowPilot 把检索拆成可观察的阶段：租户与 ACL 预过滤、候选召回、版本/有效期过滤、Rerank、证据片段选择、引用校验。最终答案只能引用仍可访问、版本有效且能回查到章节的证据。模型负责组织语言，不负责决定文档是否有权访问。

验收不能只看答案“像不像”。至少要分别报告候选召回、受限文档泄漏数、过期文档入选数、引用存在性、引用支持度和无证据回答率。故障集应包含同名旧文档、权限刚撤销、跨租户近重复文档和恶意知识内容。

残余风险在于知识元数据本身可能错误，Rerank 也可能稳定地偏向热门文档。因此摄取链路需要版本、来源和失效机制；检索质量改进必须使用固定快照做回归，不能边换知识库边比较模型。

### 4.2 长链路中断后，任务从哪里继续

**关联功能：** FP-FLOW-001、FP-FLOW-004、FP-FLOW-005、FP-DATA-002

进程日志显示“节点执行过”不等于业务状态已经可靠提交。Provider Session、Redis 队列消息和内存中的 Agent 历史都不能回答：哪一个业务节点已完成、审批是否仍有效、上一个写动作是否已经发生。

FlowPilot 只允许 LangGraph 持有跨业务节点的流程状态，PostgreSQL 保存 Task、Checkpoint 和恢复所需的安全引用。Provider Session 只是节点内适配信息，Redis 只承担信号、缓存和限流。恢复时先读取事实源，再用 Lease 与 `run_generation` fencing 阻止旧 Worker 继续写。

必须注入 Worker 强杀、Redis 清空、Checkpoint 写入失败、租约过期和旧进程延迟复活。验收关注节点调用次数、Task/Thread 身份、Run 代际、重复副作用数以及恢复前后的授权重算，而不是只确认进程重新启动。

### 4.3 Agent 循环调用工具，成本上升却没有进展

**关联功能：** FP-FLOW-006、FP-AGT-001、FP-AGT-003

循环可能来自模型反复选择同一工具、工具错误描述诱导重试、Handoff 在多个 Agent 间来回跳转，或状态没有记录“已经尝试过什么”。增加最大轮数只能止损，不能解释任务为何没有进展。

图层使用确定性路由、步骤预算、时间/Token/成本预算和重复动作指纹；Agent Runtime 只在有界节点内执行循环。相同工具、相同规范化参数和相同状态版本反复出现时，流程进入稳定失败或转人工，而不是继续让模型决定是否重试。一个节点只选择一个 Provider，避免两个 Provider 的 Session 同时声称拥有流程状态。

可观察信号应包括节点访问次数、动作指纹、Handoff 边、预算消耗和最后一次有效状态变化。测试要覆盖同参数重复、A→B→A Handoff、工具持续 503、业务错误被误判为瞬时错误。

### 4.4 长对话膨胀与指令漂移

**关联功能：** FP-CTX-001～FP-CTX-005

把完整聊天记录、检索全文和所有工具结果持续追加到 Prompt，会同时带来 Token 增长、陈旧信息干扰和权限继承。摘要本身也会漂移：用户声称的内容可能在几轮后被写成“系统已验证”。

FlowPilot 以 `ContextEnvelope` 分层注入任务事实、对话摘要和检索证据，显式记录来源、信任等级、数据分类、Token 预算和裁剪原因。摘要区分“用户声称、系统验证、模型推断”。Handoff 不转发上游 Agent 的全部消息，而是按接收角色重新计算上下文和工具集合。

验收需要 50 轮长对话、过期证据、相互矛盾的用户陈述、分类上限变化和 Handoff 禁止字段。报告同时记录 P50/P95 Token、逐层分布、任务成功、引用和安全回归。输入 Token 降低多少只能由固定消融实验得出。

### 4.5 写请求超时：重试还是等待

**关联功能：** FP-MCP-003～FP-MCP-005、FP-DATA-001

远程系统可能已经创建工单，但响应在网络中丢失。此时“失败后重试”会制造重复工单；只看本地 Checkpoint 也无法证明远程动作未发生。

FlowPilot 为写动作建立不可变 PlannedAction，绑定策略、审批、工具 Schema 和幂等键。MCP Gateway 在 PostgreSQL 执行账本中占位，再调用上游并回读。无法判断结果时进入 `UNKNOWN`，只允许对账；只有权威查询证明未执行，才能继续原逻辑动作的重试。

必须测试上游成功后断网、回读超时、上游不支持幂等、账本提交失败和重复投递十次。关键指标是逻辑写入数、未知状态停留时间、人工对账数和权威未执行证明，不是重试成功率。

### 4.6 审批已经通过，但动作已经不是原来的动作

**关联功能：** FP-APR-001～FP-APR-003

只保存 `approval_id` 或自然语言说明，无法阻止批准后替换参数、工具版本、策略版本或目标资源。审批还可能在权限撤销或有效期结束后被重放。

审批必须同时绑定租户、主体、任务、`action_digest`、Tool Schema Hash、原 PolicyDecision、策略版本和 `expires_at`。恢复和执行前重新授权，并再次比较全部绑定；任意差异都使旧审批失效。职责分离由可信身份确定性计算，不能只相信记录中的布尔值。

负向测试至少逐个修改参数、请求人、工具 Schema、策略版本、过期时间和审批人。一次只改一个字段，确保每条不变量有独立失败证据。

### 4.7 MCP 工具本身成为攻击输入

**关联功能：** FP-MCP-001、FP-MCP-002、FP-SEC-005～FP-SEC-008

工具描述、返回文本、附件和错误信息都可能包含“忽略规则”“把数据发送到某地址”等恶意指令。把 MCP 当作可信插件系统，会把模型的文本理解能力误用成安全边界。

FlowPilot 只允许 Gateway 连接上游 MCP。工具 Schema 固定并计算 Hash，工具按 Agent、租户、用途和风险进入白名单；出站网络、短时凭据、DLP 和结果 Schema 由确定性代码执行。工具输出作为不可信数据进入 Context，不能扩大权限。原始附件先隔离、扫描、解析和脱敏，只向多模态模型提供 Observation。

测试应包含恶意 Tool Description、输出中的 Prompt Injection、Schema 漂移、伪造 MIME、内网 URL、凭据片段和超大返回。检测器漏报时，授权与网络边界仍必须阻止写入和数据外传。

### 4.8 多租户隔离不能只靠查询条件

**关联功能：** FP-SEC-001～FP-SEC-004

应用代码漏写一个 `tenant_id` 条件、缓存键缺少租户前缀，或检索在召回后才做 ACL 过滤，都可能造成越权读取。模型输出中的租户字段不能成为可信依据。

SecurityContext 来自可信认证边界并以引用和 Hash 传递；Application、Policy、Gateway 与 Persistence 分别重验必要绑定。PostgreSQL 使用强制 RLS 和最小数据库角色，检索在召回前做租户/ACL 过滤，缓存与幂等键均带租户作用域。任何冲突采用 deny-overrides。

故障注入要故意删除应用过滤、伪造 Header、复用另一租户的对象 ID、污染缓存键和提交跨租户 ToolRequest。验收结果只有一个可接受值：成功跨租户读写为 0。

### 4.9 可观测数据很多，却无法回答“发生了什么”

**关联功能：** FP-OBS-001～FP-OBS-003

Trace 适合性能分析，可以采样；Audit 与 Security Event 用于责任和处置，不能因采样消失。把三类信号写进同一个日志流，会同时造成证据缺失、查询越权和敏感信息扩散。

FlowPilot 分别路由 Trace、Audit 和 Security Event，使用 `task_id`、`trace_id`、`correlation_id` 和脱敏引用关联。被阻断的 Audit 与 Security Event 双向绑定；Audit 使用追加写和哈希链，生产环境还需外部链头锚或签名。

验收要关闭 Trace 采样、断开审计下游、篡改历史记录、制造序号缺口和错链。三类信号不得保存密钥、完整 Prompt、隐藏思维链或原始附件。

### 4.10 评测通过了，但指标不可信

**关联功能：** FP-EVAL-001～FP-EVAL-005、FP-OPS-002

常见失真包括删除失败样本、把隔离样本移出分母、测试集随实现变化、让 Judge 判断工具是否真实成功，以及报告只保存平均值而没有逐 Case 结果。

FlowPilot 固定 Dataset、Fixture、Registry 和内容 Hash，以 `all_declared_cases` 为分母；失败、跳过和隔离全部计失败。权限、租户、审批、状态、工具结果和审计只能由确定性断言判定，Judge 只评价语义，并接受盲测人工校准。报告从逐 Case 原始结果生成。

评测管线本身也需要负向测试：零 Case、缺失结果、重复结果、Hash 漂移、Judge 越界、高 Judge 分覆盖确定性失败、执行失败被错误提升为通过。指标没有这些门禁，就只能视为实验输出，不能作为发布证据。

### 4.11 图能运行，却变成只能猜测的黑箱

**关联功能：** FP-FLOW-001、FP-FLOW-004～FP-FLOW-006、FP-OBS-001、FP-OPS-002

Agent 链路出错时，如果只能看最终回答和零散日志，很难区分是路由错误、Context 裁剪、Provider 重试、Handoff 回环、Interrupt 恢复错位，还是旧 Worker 越过 Lease。把完整 State 和 Prompt 全量写日志虽然“看得见”，却又会泄露敏感数据，并把调试存储误当业务事实源。

FlowPilot 让 Worker 和 Studio 使用同一个 graph factory，以稳定节点 ID、条件边和拓扑快照避免两套图漂移。Studio 只消费白名单 `debug_projection`：展示当前节点、预算、重试、Interrupt、Handoff、checkpoint sequence、`run_generation` 和 Context 层级，不展示隐藏思维链、凭据、原始附件或完整敏感资料。Studio Thread 只是开发游标，PostgreSQL Task、Checkpoint、Lease 和账本仍是事实源。

验收不仅要“能打开 Studio”，还要故意制造错误路由、过期 Lease、旧 `run_generation`、重复恢复、Context 超限、Handoff 回环和敏感字段。图上路径、结构化事件和持久化事实必须互相对齐；Studio 编辑隔离状态不能改变生产事实。具体设计见 [`LANGGRAPH_STUDIO.md`](./LANGGRAPH_STUDIO.md)。

### 4.12 多会话研发采用星形汇报，中心会话反而成为队列

**关联功能：** FP-OPS-002

**工程主题：** Multi-Agent 研发编排

**证据等级：** IMPLEMENTED

最初的七会话协作是星形结构：S2～S7 每完成一步都返回 S1，S1 再复制下一条指令。它的优点是控制直观，但会把中心会话变成串行消息队列；开发会话等待的不是代码依赖，而是重复授权。聊天摘要一旦遗漏 Head、Attempt 或停止条件，还会造成状态漂移。

FlowPilot 后来把会话视为稳定能力所有者，把 Work Package、Git Head、Contract Digest 和 Evidence 当作任务状态。依赖明确的链路由 S1 一次性授权，生产者直接交给下一消费者；消费者校验 Head、摘要、路径和证据后继续。S7 在独立组合树执行总装验证，只有异常或最终裁决返回 S1。这是从“星形图聊天编程”转向 Symphony 式工作编排：中心保留架构、安全和发布权，但不参与每次正常状态转换。

Codex 客户端的任务唤醒可以进一步移除人工复制：生产者用结构化信封唤醒下一消费者，最后由 S7 唤醒 S1。唤醒仍不是状态提交；消息必须带幂等身份，消费者从 Git 和证据恢复，并在 S1 final 停到用户门禁。具体规则见 [`THREAD_WAKE_PROTOCOL.md`](../team/THREAD_WAKE_PROTOCOL.md)。

这次 WP-040 还暴露了新的边界：S7 候选分支的身份/路径校验不能原样套用到 S1 最终合并分支。正确做法是分开验证 candidate phase 与 final phase，并证明 S1 控制面增量没有改写产品树。第一次发现这类组合问题会慢，因为需要建立失败模型和验证器；后续相同候选只运行 FAST final gate，不重复完整 Compose 发布演练。

这种协作与产品 Agent 面临的是同一类问题：

| 研发协作问题 | 产品 Agent 对应问题 | 采用的结构 |
|---|---|---|
| 聊天窗口保存工作状态 | Provider Session 被误当 Checkpoint | Git/Work Package/Evidence 是事实源 |
| 每步都回 S1 | 每节点都回中心 Router | 预授权有序链与消费者门禁 |
| 重复派发 | 重复工具写入 | Attempt/Head 幂等身份 |
| 会话越权改共享文件 | Agent 越权调用工具 | 路径所有权、单写者、契约优先 |
| 最终分支规则误用候选规则 | 恢复阶段复用过期授权 | 分阶段重验身份、作用域和事实 |
| 全量门禁每步重跑 | 所有错误都盲目全链重试 | FAST/STANDARD/RELEASE 分级与精确缓存键 |

残余风险是消费者可能错误接受上游证据，或预授权范围过宽。因此 R3、契约变化、路径越权、风险升级和门禁失败必须暂停并交回 S1；`CONSUMER_ACCEPTED` 只解锁下一步，不等于批准合并。
